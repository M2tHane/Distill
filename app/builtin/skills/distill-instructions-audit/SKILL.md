# 检查指令文件是否过时

指令文件每次都会进入 agent 的上下文。它过时了，agent 就会按旧的做法做事，用户却往往不知道原因。目标：找出**已经不对的、互相矛盾的、该补没补的**内容，给出具体改法，由用户决定改不改。

## 输入

- `runs/<id>/instructions/README.md`：每个指令文件的原路径、适用的项目、最后修改时间、之后项目的提交数和最近的提交、文中提到但现在找不到的路径。副本在同一目录。
- 会话记录 `runs/<id>/*.md`：能看到 agent 实际怎么做、用户怎么纠正、哪些命令失败了。
- 项目本身（路径见 README 里的“适用于”）：可以读文件核实（`package.json`、`go.mod`、`Makefile`、目录结构、脚本、配置），但**不要修改任何项目文件**。

## 步骤

1. 读 README，先看信号最强的：
   - 找不到的路径：逐个核实是改名、搬走还是删除了（可以在项目里搜索同名文件）。
   - 很久没改、之后又有很多提交的文件：看最近的提交在改什么（新目录、换了依赖、换了构建方式），对照指令文件里的描述。
2. 逐条读指令文件，把可核实的陈述列出来：命令（安装、构建、测试、运行、发布）、目录结构、技术栈和版本、代码约定、流程要求（分支、提交、审查）。对每条找证据：
   - 项目文件：命令在 `package.json` / `Makefile` / 脚本里还在吗？目录和文件还在吗？依赖和版本还是这样吗？
   - 会话：agent 照着做之后**失败了**吗（看 `→ failed` 和报错）？用户**纠正过**吗（“不是用 npm，用 pnpm”“那个目录已经不用了”）？agent 实际用的是另一套做法并且成功了吗？
3. 判定每条的状态：
   - **过时**：与项目现状或会话中成功的做法矛盾。
   - **冲突**：同一个项目的几个指令文件之间、项目级与用户级之间说法不一致（例如 CLAUDE.md 和 AGENTS.md 对测试命令说法不同），或与用户在会话里的明确要求矛盾。
   - **缺失**：会话里用户反复交代、或 agent 反复踩坑的事，指令文件没写。
   - **可疑**：证据不足，只能提醒用户确认。
   没有问题的条目不用列出。
4. 每条问题给出具体改法：原文 → 建议改成的文字（或“删除”），并写明依据。
5. 只写有证据的结论；证据只来自快照和会话的，写明“未在项目文件中核实”。

## 输出

写一个文件 `library/reports/<YYYY-MM-DD>-<项目名>-instructions-audit.md`（多个项目用 `multi`）：

```markdown
---
name: <与文件名相同，不含 .md>
description: <一句话：检查了哪些文件，发现几处过时或冲突>
---

# 指令文件检查：<项目名>

> 检查了：`<原路径>`（最后修改 YYYY-MM-DD，之后 N 次提交）……

## 结论
- <最需要马上改的 1～3 处>

## 问题
### `<原路径>`
| 状态 | 原文 | 证据 | 建议改为 |
|---|---|---|---|
| 过时 | `npm run dev` | package.json 已无 dev 脚本；会话 02 中失败 2 次，后来用 `pnpm dev` 成功 | `pnpm dev` |

## 建议补充
- `<建议加的那一行>` —— 依据：…

## 修改后的完整片段（可选）
<改动较多时，给出修改后的整段，方便用户直接替换>
```

用用户使用的语言写作。没有发现问题时也写报告，说明检查了什么、为什么认为它仍然准确。

## 结束

告诉用户报告的路径和最需要改的地方。提醒用户：Distill 不会改项目里的指令文件，需要用户自己改（或让 agent 按报告改）。
