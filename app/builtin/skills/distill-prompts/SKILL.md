# 提示词诊断

目标：用用户**自己写过的提示词**做例子，让用户知道哪种写法让 agent 做错或做慢了，下次该怎么写。语气是教练，不是批评；只谈提示词，不评价人。

## 输入

- 会话记录 `runs/<id>/*.md`：`## User` 是用户的原话；助手回复后面的 `_(interrupted by the user)_` 表示用户打断，工具调用后的 `→ rejected by the user` 和 `>` 是用户拒绝和理由，`→ failed` 是失败的调用。
- `runs/<id>/instructions/README.md`（如果有）：项目的指令文件。提示词里反复交代的内容，可能本该写进指令文件。

## 怎样判断一条提示词有问题

只在有**后果**时才算问题。后果的信号：
- 用户随后纠正（“不是这个意思”“我说的是……”“不要……”“又错了”）；
- 用户打断助手，或拒绝了工具调用；
- 助手反问澄清，或做了与需求不符的事后又返工；
- 同一个要求在多个会话里重复交代；
- 助手做了很多无关的工作，或很久才进入正题。

对每个有后果的提示词，判断属于哪类原因：
1. **目标不清**：没说要什么结果，或一句话里混了多个目标。
2. **缺上下文**：没给出文件、报错原文、复现步骤、相关约束，让 agent 去猜。
3. **缺验收标准**：没说怎样算完成（要跑什么测试、要什么输出格式、改到什么程度）。
4. **范围和约束不明**：没说哪些不能动、要不要提交、能不能装依赖、要不要先给方案。
5. **指代模糊**：“这个”“上面那个”“改一下”指向不明。
6. **一次塞太多**：多个独立任务挤在一条消息里，结果漏做或做乱。
7. **该写进指令文件的**：每个会话都要重复说的偏好和规则。

## 步骤

1. 通读所有 `## User`，标出有后果的提示词，记下证据（会话文件名、原话、后果）。
2. 按上面的原因归类，统计每类出现的次数，找出用户**最常见的 2～4 个习惯**。
3. 每个习惯挑 1～3 个最典型的例子，写出：原提示词 → 发生了什么 → 改写后的提示词 → 为什么这样写更好。改写要贴合原意和原来的语言风格，不要凭空加需求。
4. 总结一份用户可以直接套用的提问模板（按用户实际常做的任务类型写，例如“修 bug”“加功能”“重构”），每个模板不超过 6 行。
5. 列出应该写进 CLAUDE.md / AGENTS.md 的内容（用户反复在提示词里交代的），写出建议的那一行。
6. 也写 1～2 个用户做得好的例子，说明好在哪里，方便保持。
7. 如果会话太少或提示词都没有明显后果，如实说明，不要硬找问题。

## 输出

写一个文件 `library/reports/<YYYY-MM-DD>-prompts.md`：

```markdown
---
name: <与文件名相同，不含 .md>
description: <一句话：分析了多少条提示词，最主要的改进点>
---

# 提示词诊断

> 范围：N 个会话，M 条用户消息，其中 K 条导致了纠正、打断或返工。

## 最需要改的习惯
1. <习惯>（出现 N 次）：一句话说明后果

## 例子
### <习惯>
- 原话（`<会话文件名>`）：“…”
- 结果：…
- 可以这样写：
  > …
- 为什么：…

## 提问模板
### 修 bug
…

## 建议写进指令文件
- `<要加的那一行>` —— 你在 N 个会话里都交代过

## 做得好的地方
- …
```

用用户使用的语言写作。

## 结束

告诉用户报告的路径，并用一句话说出最值得先改的那个习惯。
