# 从会话提炼 Skill

Skill 是 agent 在遇到同类任务时才加载的操作手册。好的 Skill 让下一次少走这次走过的弯路：**照着做能一次做对**。

## 输入

用户在消息里引用了若干会话记录（`runs/<id>/*.md`）：
- `## User`：用户的输入；`## Assistant`：助手的回复和 `- **工具名** 摘要` 形式的工具调用。
- 工具调用后的 `→ failed` 带报错摘录，`(the same error as before, Nth time)` 表示同一错误重复出现；标题下的 `> Errors that repeated:` 汇总了重复的错误。
- `→ rejected by the user` 和后面的 `>` 是用户拒绝的操作和理由，`_(interrupted by the user)_` 是用户打断——这两者通常说明助手的做法不对。
- 成功的命令只保留了简短输出（例如测试结果），读取文件、搜索的结果没有保留。

## 什么值得做成 Skill

满足下面至少一条，并且步骤稳定：
- **会重复的任务**：同一类任务出现在多个会话里，或用户说了“以后也要这样”。
- **踩过坑才做对的流程**：中间有失败、返工、用户纠正，最后找到了正确做法——把正确做法和坑一起写下来，这是最有价值的 Skill。
- **项目或工具链特有的做法**：特定的构建/发布/调试步骤、内部工具的正确用法、必须遵守的顺序。

不要做成 Skill：一次性的任务、通用常识（“写测试”“读文档”）、只有一个会话且没有踩坑的普通操作。只适合写成一句约束的，建议用户改用 distill-rule。

## 步骤

1. 读 `library/README.md`，浏览 `library/skills/` 下已有的 skill。能扩充已有 skill 的就改它，不要新建重复的。
2. 读完所有被引用的会话。对每个候选流程，整理：
   - 触发场景：用户当时说了什么、在做什么；
   - 最终成功的步骤和命令（以**成功的那次**为准，失败的写法进“常见坑”）；
   - 失败和纠正：报错原文 → 原因 → 正确做法；
   - 怎样确认做对了：会话里用来验证的命令和它们成功时的输出。
3. 每个 skill 写成 `library/skills/<name>/SKILL.md`：
   - front matter：`name`（小写连字符，与目录同名）、`description`。description 决定 agent 会不会调用它：写清楚**做什么**和**什么时候用**，包含用户会说的关键词。
   - 正文：
     - 适用场景与前置条件（需要的工具、环境变量、目录）；
     - 步骤：编号，每步能直接执行（命令、要改的文件、要检查的输出）；
     - 常见坑：表格“症状（报错原文的关键句）→ 原因 → 解决”，来自会话里的失败；
     - 完成标准：跑什么、看到什么才算完成。
   - 只写会话里有依据的命令、路径和参数，不要编造；会话里没验证过的写“未验证”。
   - 内容长时把细节放进 `references/*.md`，SKILL.md 里写明何时读它；可复用的脚本放进 `scripts/`。
4. 用用户使用的语言写作。

## 结束

列出新建或修改的文件，每个附一句说明（它解决哪个会话里的什么问题）。如果找不到值得做成 skill 的流程，直接说明原因，不要硬写。
