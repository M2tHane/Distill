# 项目问题诊断

目标：让用户看完报告就知道这个项目在开发中**反复在哪里出问题、浪费了多少、该怎么根治**。报告是给人看的，不是给 agent 的指令。

## 输入

- 会话记录 `runs/<id>/*.md`：
  - front matter 里的 `tool_calls`、`tool_failures`、`interruptions` 是整场会话的统计；
  - 标题下的 `> Tools: …` 和 `> Errors that repeated:` 汇总了重复出现的错误及次数；
  - `## User` 是用户输入，`## Assistant` 是助手的回复和工具调用；
  - 工具调用后的 `→ failed` 带有报错摘录，`→ failed (the same error as before, Nth time)` 表示同一个错误又出现了；`→ rejected by the user` 后的 `>` 是用户拒绝时说的话；`_(interrupted by the user)_` 表示用户打断了助手。
- `runs/<id>/instructions/README.md`（如果有）：项目的 CLAUDE.md / AGENTS.md 副本和它们的新旧程度。
- 需要核实时可以读项目里的文件（路径在会话的 `cwd`），但不要修改。

## 步骤

1. 先读每份记录的 front matter 和开头的错误汇总，按失败次数从多到少排出要细看的会话。
2. 逐个会话读，记录下面几类问题，每条都要有证据（会话文件名 + 原话或报错的摘录）：
   - **反复出现的报错**：同一个错误出现 2 次以上，或者助手换了几种写法才绕过去。找出根因（环境缺东西、命令写法和 shell 不兼容、权限/沙箱限制、依赖版本、配置缺失……），而不是只罗列现象。
   - **弯路**：助手做了又撤销、来回改同一处、跑偏后被用户纠正、用错工具或用错目录。估算浪费了多少轮/多少次工具调用。
   - **验证缺口**：改完没有跑测试或没有构建、测试本身不可靠、用户发现了助手没发现的问题。
   - **环境与工具链的坑**：缺少命令（`command not found`）、路径不存在、端口占用、版本不一致、需要特定启动方式等。
   - **流程和协作问题**：用户频繁打断或拒绝、需求反复变更、一次塞了太多任务、助手没问清楚就动手。
   - **项目本身的问题**：代码结构、配置、文档缺失、指令文件过时（如果指令文件快照里有已不存在的路径或很久没更新，简单提一句，并建议用 distill-instructions-audit 细查）。
3. 合并同类问题，按**影响**排序：出现次数 × 每次浪费的成本；会导致错误结果的排在只是慢的前面。
4. 对每个问题给出**可执行的根治办法**，并标明落地方式：
   - 改项目（加脚本、补依赖、修配置、补测试）；
   - 改指令文件（给出要加/改的那一行）；
   - 沉淀成 Skill 或 Rule（写明建议的名字，用户可以再用 distill-skill / distill-rule 生成）；
   - 改用户的提问方式（建议用 distill-prompts 细看）。
5. 不要编造：会话里没有证据的不写；拿不准根因的写“推测”并说明依据。

## 输出

写一个文件 `library/reports/<YYYY-MM-DD>-<项目名>-review.md`（小写英文和连字符；多个项目用 `multi`）：

```markdown
---
name: <与文件名相同，不含 .md>
description: <一句话：哪个项目、几个会话、最主要的问题>
---

# <项目名> 开发问题诊断

> 范围：N 个会话（日期区间），工具调用 X 次，失败 Y 次，用户打断 Z 次。

## 结论
<3～5 条，最重要的放最前，每条一句话>

## 问题清单
### 1. <问题标题>（影响：高/中/低，出现 N 次）
- 现象：…
- 证据：`<会话文件名>`：“<摘录>”
- 根因：…
- 建议：…（落地方式：改项目 / 改指令文件 / 做成 Skill / 改提问方式）

## 反复出现的错误
| 错误 | 次数 | 出现在 | 根因 | 解决办法 |

## 建议沉淀
- Skill：<name> — <它能避免哪个问题>
- Rule / 指令文件：<要加的那一行>
```

用用户使用的语言写作。篇幅以能看完为准：问题清单通常 3～10 条，不要凑数。

## 结束

告诉用户报告的路径，并用 3 句话以内概括最重要的发现。
